Your billing report endpoint was fine with 50 brands. Now there are 4,000 and it times out. Nobody touched the code. <mark>The input changed.</mark> Big-O is the tool that predicts that phone call before it happens.

## What Big-O actually says

Big-O describes <mark>how cost grows as the input grows</mark>. It ignores constants and small terms because, at scale, the shape of the curve wins. It tells you nothing about how fast something is today, only how it ages.

| Class | n = 1,000 | Feels like |
| --- | --- | --- |
| O(1) | 1 | Hash lookup |
| O(log n) | ~10 | Index lookup, binary search |
| O(n) | 1,000 | One pass over the list |
| O(n log n) | ~10,000 | A good sort |
| O(n²) | 1,000,000 | Loop inside a loop |
| O(2ⁿ) | a number with 302 digits | Trying every subset |

<Quiz>

Roughly what's the complexity here, and what's the cheapest fix?

```ruby
admins = Admin.pluck(:email)          # Array, m items
users.select { |u| admins.include?(u.email) }  # n users
```

- [ ] O(n), it's already fine
- [x] O(n·m). Make admins a Set, which gets you to O(n + m)
- [ ] O(log n). Sort users first
- [ ] O(n²). Can't be improved

<Why>

`Array#include?` scans the whole array, so every user costs m comparisons. `admins.to_set` makes each lookup O(1) on average. Total: build the set once (m) plus one pass over users (n).

</Why>

</Quiz>

## Why hashes feel like magic

A hash function turns a key into a bucket number, so a lookup goes straight to the right bucket and never scans. That's <mark>O(1) on average</mark>. Worst case is O(n) when everything collides into one bucket, which good hash functions make vanishingly rare. Ruby's `Set` is built on `Hash`, so it gets the same speed.

<Note>

Rule of thumb from code review: if you see `.include?`, `.find`, or `.detect` inside a loop, ask whether a hash or set keyed by that value should exist.

</Note>

## log n means halving

Every time you can throw away half the remaining work, you're in log territory. Binary search on a billion sorted rows needs about <mark>30 steps</mark>, because 2³⁰ ≈ 1,000,000,000. Database indexes are trees built on this idea, which is why an indexed lookup on 300M rows still feels instant.

```ruby
Math.log2(1_000_000_000) # => 29.897...
```

<Myth fact={false}>

An O(1) operation is always faster than an O(n) one.

<Why>

Big-O hides constants. Scanning an array of 8 items can beat hashing a key, and a cache-friendly linear scan beats pointer-chasing for small n. Big-O tells you who wins eventually, not who wins at n = 8.

</Why>

</Myth>

## Amortized: cheap on average, spiky sometimes

`array << item` is O(1) <mark>amortized</mark>. Most pushes are trivial, but when capacity runs out Ruby allocates a bigger buffer and copies everything, which is O(n). Because capacity grows geometrically, those copies are rare enough that the average per push stays constant.

<Note>

Think of a hotel chain: most weeks you add a room, and occasionally you open a whole new building. Averaged over the year, rooms are cheap to add.

</Note>

## The complexity you meet at work

In Rails apps the expensive n is rarely CPU. It's <mark>round trips and memory</mark>.

- **N+1 queries** are O(n) network round trips. `includes` collapses them into 2 queries.
- `User.all.each` holds every record in memory: O(n) space. `find_each` keeps it at O(batch size).
- Sorting in Ruby what the database could sort with an index is O(n log n) work you didn't need.

<Quiz>

You swap `User.all.each` for `User.find_each` on 5M rows. What actually improves?

- [ ] Time complexity drops from O(n) to O(log n)
- [x] Peak memory: records load in batches of 1,000 instead of all at once
- [ ] It skips users that haven't changed
- [ ] Nothing, it's an alias

<Why>

You still visit every row, so time stays O(n). The win is space: `find_each` paginates by primary key, so memory stays flat no matter how big the table gets.

</Why>

</Quiz>

<Quiz>

Find two invoice amounts that sum to a target. The nested loop is O(n²). What's the classic O(n) move?

- [ ] Sort, then nested loop
- [x] Walk once and keep a hash of amounts seen. For each x, check whether target − x is already in it
- [ ] Use recursion
- [ ] Split the array in half

<Why>

Trading memory for time is the most common optimization there is. One pass plus O(1) hash lookups gives O(n) time and O(n) space. (Sort + two pointers also works at O(n log n).)

</Why>

</Quiz>

<Interview>

A nightly job dedupes 2 million subscription events by (account_id, event_type, day) and takes 40 minutes. Walk me through how you'd analyze and speed it up.

<Rubric>

- Measures before guessing: profiles, benchmarks, finds where time goes (DB vs Ruby)
- Identifies likely quadratic behavior (include?/find in a loop) and states the complexity
- Uses a hash/set keyed on the composite tuple for O(n)
- Considers pushing the work into SQL (GROUP BY, DISTINCT ON, unique index + upsert)
- Watches memory: batches/streams instead of loading 2M records
- Mentions verifying correctness and results after the change

</Rubric>

<Answer>

**Measure first.** Is it DB time or Ruby time? A quick profile usually shows something like `events.find { ... }` inside a loop, which makes it O(n²).

**Fix the algorithm.** Key a `Set` on `[account_id, event_type, day]`, one pass, O(n).

**Better: let Postgres do it.** `SELECT DISTINCT ON (account_id, event_type, date_trunc('day', created_at)) ...`, or prevent duplicates entirely with a unique index and `insert_all ... on conflict do nothing`.

**Mind memory.** Stream with `find_each`/`in_batches`. **Verify** with counts before and after, and keep the old path behind a flag until the numbers match.

</Answer>

</Interview>

<CheatSheet>

- Big-O = how cost grows with n. Shape, not speed.
- `.include?`/`.find` in a loop → build a hash or set.
- log n = halving. 1B items ≈ 30 steps.
- Constants matter at small n; Big-O wins at large n.
- At work, the costly n is usually round trips and memory.

</CheatSheet>
