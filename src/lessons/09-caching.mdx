'There are only two hard things in computer science: cache invalidation and naming things.' This app is called Cache Warmup, so let's get the other one right. <mark>A cache is a bet that data won't change before you read it again.</mark>

## Layers, and why they exist

Each layer is closer and faster than the next one down. Rough latencies are worth knowing for system design talks:

| Where | Roughly |
| --- | --- |
| CPU L1 cache | ~1 ns |
| Main memory | ~100 ns |
| SSD random read | ~100 µs |
| Round trip in the same datacenter (e.g. Redis) | ~0.5 ms |
| Round trip across an ocean | ~150 ms |

<Note>

Web layers, outermost first: browser → CDN → reverse proxy → app cache (Redis/Memcached) → database buffer cache.

</Note>

## Read and write patterns

- **Cache-aside** (the default): read the cache; on a miss, load from the DB and fill it. `Rails.cache.fetch` is exactly this.
- **Write-through**: write to cache and DB together. Reads are fresh; writes are slower.
- **Write-back**: write to cache now, DB later. Fast, but you can lose data.
- **Write-around**: write only to the DB and let reads fill the cache.

## Invalidation strategies

- **TTL**: accept staleness up to N seconds. Simple and bounded.
- **Delete on write**: precise, but easy to forget a code path.
- **Key-based expiration**: put the version in the key so <mark>you never invalidate</mark>; new data simply lives at a new key and old entries age out. Rails' `cache_key_with_version` does this.

```erb
# Russian doll: the outer cache auto-busts when an inner record changes
class LineItem < ApplicationRecord
  belongs_to :invoice, touch: true
end

<% cache invoice do %>          <%# key includes invoice.updated_at %>
  <% invoice.line_items.each do |li| %>
    <% cache li do %> ... <% end %>
  <% end %>
<% end %>
```

<Quiz>

With key-based expiration (`cache invoice`), what happens when the invoice is updated?

- [ ] You must call Rails.cache.delete
- [x] updated_at changes the key, so the next read misses and fills a fresh entry; the old one gets evicted eventually
- [ ] The cache serves stale data forever
- [ ] Redis notices and deletes it

<Why>

The key includes a version (updated_at), so nothing needs deleting. You trade some memory for never forgetting an invalidation path.

</Why>

</Quiz>

## How caches fail

- **Stampede / dogpile**: a hot key expires and 500 requests all miss and recompute at once. Fixes: `race_condition_ttl`, a lock so one request recomputes, early probabilistic refresh, serving stale while revalidating.
- **Penetration**: lookups for keys that don't exist always miss. Cache the 'not found' too, briefly.
- **Hot keys**: one key gets all the traffic on one Redis node.
- **Eviction**: when memory is full, Redis' policy decides. The default `noeviction` makes writes fail; caches usually want `allkeys-lru` or `allkeys-lfu`.

<Quiz>

Every hour at :00 the homepage stats key expires and DB CPU spikes to 100%. What is this, and what fixes it?

- [ ] A memory leak; restart Redis
- [x] A cache stampede. Use race_condition_ttl / a recompute lock / serve stale while one request refreshes
- [ ] Too many indexes
- [ ] Network partition

<Why>

Synchronized expiry plus an expensive recompute makes a dogpile. Let one request rebuild while everyone else gets the slightly stale value.

</Why>

</Quiz>

<Myth fact={false}>

Adding a cache always reduces database load.

<Why>

A low hit ratio, stampedes on expiry, and cache-penetration misses can make load spikier than before. Measure the hit rate, and protect the miss path.

</Why>

</Myth>

<Quiz>

The browser sends `If-None-Match: "abc123"` and the resource hasn't changed. Ideal response?

- [ ] 200 with the full body
- [x] 304 Not Modified, no body
- [ ] 204 No Content
- [ ] 302 to itself

<Why>

ETags enable conditional requests. A 304 saves bandwidth and rendering. Rails' `fresh_when` / `stale?` handle this.

</Why>

</Quiz>

## What not to cache (casually)

Be careful caching <mark>balances, permissions, and anything a user just changed</mark> (read-your-writes surprises). Cache keys must include everything that changes the output, like locale, currency, plan, and permissions, or one customer sees another's data. That bug is a lot worse than a slow page.

<Interview>

A shipping-rate calculator page is slow because rates come from 6 carrier APIs. How would you use caching here, and what could go wrong?

<Rubric>

- Identifies what is cacheable and the key (origin, destination, weight/dimension bucket, service, account pricing)
- TTL tied to how long carrier rates are valid
- Stampede protection and serve-stale/fallback when a carrier is down
- Fetches carriers in parallel with timeouts; partial results are OK
- Re-quotes or validates the price at checkout/booking for correctness
- Measures hit rate and latency; considers key cardinality/memory

</Rubric>

<Answer>

**Cache the carrier responses** per `(carrier, origin zip, dest zip, weight bucket, dims bucket, service, account pricing tier)`. Bucketing weights raises the hit rate. The TTL comes from the carrier's quote validity (minutes to hours).

**Protect the miss path:** call carriers in parallel with tight timeouts, show what returned, and use a recompute lock plus serve-stale so a hot route doesn't stampede.

**Correctness:** a cached rate is for display. Re-quote (or validate against a short TTL) at booking, because the price you charge must be right.

**Measure:** hit ratio per carrier, p95, key count. Cache-key mistakes that mix up account pricing are the scary bug, so test them.

</Answer>

</Interview>

<CheatSheet>

- Cache = a bet that data won't change before the next read.
- Cache-aside by default; key-based expiration avoids invalidation bugs.
- Stampedes: lock, stale-while-revalidate, jitter.
- Cache 'not found' briefly; set an eviction policy.
- Keys must include everything that changes the output.

</CheatSheet>
