The moment you have two services and a network between them, you have a distributed system. <mark>A timeout doesn't mean it failed. It means you don't know.</mark> Most of this lesson is about living with not knowing.

## The fallacies

Classic list of things people wrongly assume: the network is reliable; latency is zero; bandwidth is infinite; the network is secure; topology doesn't change; there is one administrator; transport cost is zero; the network is homogeneous.

The practical consequence: every remote call has <mark>three outcomes</mark>, which are success, failure, and unknown.

## CAP, said correctly

When a **network partition** happens (and it will), a system must choose: stay **Consistent** (refuse some requests) or stay **Available** (answer, possibly with stale data). Partitions aren't optional, so the real choice is C or A *during a partition*.

**PACELC** adds the everyday part: <mark>Else (no partition), you trade Latency against Consistency.</mark> Synchronous replication is consistent but slower; async is faster but can serve stale data.

<Myth fact={false}>

CAP means you pick any two of Consistency, Availability, and Partition tolerance.

<Why>

You can't opt out of partitions on a real network. CAP is about what you give up when one happens: C or A. 'CA systems' only exist on a single node.

</Why>

</Myth>

## Consistency you'll actually meet

- **Strong**: every read sees the latest write.
- **Read-your-writes**: you always see your own changes.
- **Eventual**: replicas converge… eventually.

The everyday bug: write to the primary, redirect, read from a <mark>replica that's 200 ms behind</mark>, and get a 404 on the record you just created. Rails' multi-DB support sends reads to the primary for a short window after a write for exactly this reason.

<Quiz>

A user creates a subscription and the confirmation page says 'not found', but a refresh fixes it. Most likely cause?

- [ ] Cache stampede
- [x] Replica lag: the read went to a replica that hadn't caught up
- [ ] Deadlock
- [ ] DNS

<Why>

A classic read-your-writes violation. Pin reads to the primary right after writes for that user, or pass the created data along instead of re-reading it.

</Why>

</Quiz>

## Queues vs logs

**Queue** (Sidekiq, SQS, RabbitMQ): a message is consumed and gone, and workers compete for messages. **Log** (Kafka): messages are retained and each consumer group tracks its own offset, so you can replay. Ordering is guaranteed only <mark>within a partition</mark>, so partition by the key whose order matters (account_id, shipment_id).

## The dual-write problem → transactional outbox

You save the invoice to Postgres, then publish `invoice.paid` to a broker. If the process dies between the two, the DB says paid and nobody was told. Two systems can't commit atomically without heavy machinery.

**Outbox:** in the *same DB transaction*, insert the event into an `outbox` table. A relay process publishes outbox rows and marks them sent. That's at-least-once, so consumers must be idempotent (lesson 7).

<Note>

**Sagas** extend this to multi-step workflows. Charge → reserve inventory → book shipment, and if booking fails, run compensations (release inventory, refund) instead of a distributed transaction.

</Note>

<Quiz>

You need 'save order' and 'publish order.created' to never disagree. Standard pattern?

- [ ] Publish first, then save
- [ ] Wrap both in a DB transaction
- [x] Transactional outbox: write the event to an outbox table in the same transaction, relay it afterward
- [ ] Retry until both succeed

<Why>

A DB transaction can't include the broker. The outbox makes the event part of the same atomic write, and the relay delivers it at least once.

</Why>

</Quiz>

## Resilience toolkit

- **Timeouts** on every remote call. No exceptions.
- **Retries** with backoff and jitter, only for idempotent operations.
- **Circuit breaker**: after N failures, stop calling for a while and fail fast, so a sick dependency isn't hammered and your threads aren't all stuck waiting.
- **Bulkheads**: separate pools so one slow carrier can't eat every worker.
- **Rate limits and backpressure**.

<Quiz>

Kafka topic with 12 partitions. Where is message order guaranteed?

- [ ] Across the whole topic
- [x] Within a single partition
- [ ] Never
- [ ] Only with one consumer

<Why>

Order is per partition. Use the entity ID as the message key so every event for one shipment lands in the same partition, in order.

</Why>

</Quiz>

<Interview>

When an invoice is paid, the billing service must update its DB and the notification service must email a receipt. How do you keep them consistent?

<Rubric>

- Recognizes the dual-write problem
- Transactional outbox (or CDC) to publish the event reliably
- At-least-once delivery → idempotent consumer (dedupe by event id)
- Ordering concerns (partition by invoice/account) and retries/DLQ
- Accepts eventual consistency for email; reconciliation/monitoring for misses
- Mentions timeouts/unknown outcomes when calling the email provider

</Rubric>

<Answer>

The trap is the **dual write**: update the DB, then call the notifier, and crash in between. Instead, in the same transaction that marks the invoice paid, insert an `invoice.paid` row into an **outbox**. A relay publishes it to the queue or Kafka (keyed by account for ordering) and marks it sent.

The notification service is an **idempotent consumer**: it records processed event IDs (unique index) before or with sending, so redeliveries don't double-email. The email provider call gets its own idempotency key if supported.

Email being a few seconds late is fine, so eventual consistency is acceptable here. Add a DLQ, alerting on outbox lag, and a daily check that every paid invoice has a receipt.

</Answer>

</Interview>

<CheatSheet>

- Timeout = unknown, not failure.
- CAP: C or A during a partition. PACELC: latency vs consistency otherwise.
- Replica lag breaks read-your-writes.
- Outbox for reliable events; sagas for multi-step workflows.
- Timeouts, retries + jitter, circuit breakers, bulkheads.

</CheatSheet>
